# Error Handling and RFC 9457

## 1. Structured Error Envelopes

A reliable API never returns plain text or arbitrary unstructured JSON errors. Standardise on [RFC 9457 Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html) (formerly RFC 7807).

### Media Type
Set `Content-Type: application/problem+json`.

## 2. RFC 9457 Standard Fields

- **`type`** (URI reference): Identifies the problem type. Provides human-readable documentation.
- **`title`** (string): Short, human-readable summary of problem type. Should not change between occurrences.
- **`status`** (integer): The HTTP status code generated by origin server.
- **`detail`** (string): Human-readable explanation specific to this occurrence.
- **`instance`** (URI reference): Identifies the specific occurrence of the problem.

## 3. Complete Validation Error Example (HTTP 422)

```json
{
  "type": "[https://api.example.com/errors/validation-error](https://api.example.com/errors/validation-error)",
  "title": "Validation Error",
  "status": 422,
  "detail": "The request payload failed field validation rules.",
  "instance": "/orders/req_987654321",
  "code": "VALIDATION_FAILED",
  "invalid_params": [
    {
      "name": "email",
      "reason": "Must be a valid email address.",
      "code": "INVALID_FORMAT"
    },
    {
      "name": "quantity",
      "reason": "Quantity must be an integer greater than zero.",
      "code": "MIN_VALUE"
    }
  ]
}

```

## 4. Key Rules for Error Responses

1. **Machine-readable codes:** Provide a high-level `code` (e.g. `INSUFFICIENT_FUNDS`, `RESOURCE_LOCKED`) so client applications can execute programmatic branching without regex-matching strings.
2. **Field-level detail:** For form validation failures, always supply an array of invalid parameters with exact field names and specific reasons.
3. **No stack traces in production:** Never leak internal stack traces, SQL syntax, or internal system topology in error payloads.
